# 与 PRD 的偏差清单（V1.0 实现）

> **2026-10-01 更新**：本清单第 1 节的「已移除盲听」「不建知识库」两条已被 PRD V1.1 推翻——盲听在选型轮中恢复（见 `V1.1-P0-变更说明.md`），知识库排在 W3。其余条目仍有效。

本文件记录实现与 PRD 的**每一处有意偏差**、我替你做的决定，以及仍需你拍板的开放项。
评审时建议优先看第 1 节。

---

## 1. 按你的要求做的功能删改

| # | 项目 | PRD 原设计 | 现实现 | 影响 |
|---|---|---|---|---|
| 1 | **盲听选优** | F2-10 盲听模式；盲听编号 A–F；后端 `blind=true` 时不返回 `model_id`/`model_name`/原始文件名，音频地址用随机 token（§9）；§12.1 验收项之一 | **已完整移除**。候选卡片直接显示模型名与版本 | 词曲工作台少了一个"隐藏来源"的开关；模型选型的统计口径不变，但"消除品牌偏见"的作用消失，选曲时人会被品牌影响 |
| 2 | **文化知识库** | F2-2 按知识库检索生成歌词；F2-5 史实核对显示"知识库依据"；`brief.kb_refs`；§1.4 未列入范围表 | **不建知识库**，史实核对直接送 LLM（无 Key 时用本地规则：含地标词/年代表述的行标为待确认） | `brief.kb_refs` 字段保留但恒为空；史实准确性完全依赖 LLM，没有可追溯的依据来源。**这是当前最大的准确性风险** |
| 3 | **实时性** | F1-2 状态变化 5 秒内反映；F1-6 GPU 队列每 5 秒刷新 | 前端轮询 6 秒（生成/合成中为 3–4 秒） | 无功能差异，只是数值放宽 |

## 2. 技术方案的替换

| # | 项目 | PRD §10.1 | 现实现 | 原因 |
|---|---|---|---|---|
| 4 | 任务队列 | Redis + RQ（或 Celery） | **自研 SQLite 队列**（`app/queue.py`），保留 api 并发 4 / gpu 并发 1 的语义 | Windows 无原生 Redis。`queue.py` 的 `enqueue/handler/requeue` 形状对齐 RQ，将来换回 Redis 只改这一个文件 |
| 5 | 向量库 | FAISS（本地文件索引） | numpy 余弦检索（万级素材 < 50ms） | 免去一个编译型依赖（Windows 上 faiss-cpu 装起来麻烦）。数据量上来后按 PRD 迁 FAISS → pgvector，检索入口已收敛在 `adapters/clip.py` |
| 6 | 表结构 | `gpu_job`（只描述本地任务） | 泛化为 `job` 表，增加 `queue` 字段区分 api/gpu | §9 要求 `GET /api/jobs` 统一列任务，原设计无法覆盖 API 类任务 |
| 7 | 表数量 | §8 列出 15 组 | 16 张表（含新增 `ai_call`） | §11 要求"所有 AI 调用记录：模型、参数摘要、耗时、费用、结果状态"，需要一个落地表 |
| 8 | 前端依赖 | 波形用 wavesurfer.js | 已用 | 一致 |

## 3. PRD 未定义、我替你做的决定

| # | 事项 | 我的决定 | 备注 |
|---|---|---|---|
| 9 | **抽帧策略** | 固定 0.5s / 2s / 4s 三帧 | 直接决定 VLM 打标成本。接真 VLM 前建议改成镜头切换检测 + 关键帧去重，否则 1 万条素材的调用量会远超预期 |
| 10 | **"二创素材卡 JSON" 格式** | 认定为 monitor.py 的 `analysis.result_json`（含 `song/artist/why_hot/elements/remix_card/metadata`），由 `POST /api/trends/sync` 规范化为 `trend_card` 表 | PRD 说的"导入素材卡 JSON"（F1-4）现实现为导入 `analysis_YYYY-MM-DD.json`，字段映射：`elements.genre→曲风`、`remix_card.style_prompt→风格提示词`、BPM 从 `elements.bpm` 区间解析 |
| 11 | **素材卡的"周"** | 按 `analyzed_at` 的 ISO 周（如 `2026-W39`）计算 | monitor.py 里没有周的概念，只有日期 |
| 12 | **驳回后旧产物** | 全部保留在库中（不级联删除），便于人工对比 | PRD 只说"可驳回到上游状态重新生成"，没说旧产物怎么处理 |
| 13 | **"简报确认"也是人工节点** | 状态机里 `briefing → lyric_generating` 需要人工点"确认简报，开始写词" | PRD §4.2 表格里 `briefing` 的"下一状态"直接写了 `lyric_generating`，但 §3 S1 和 §1.3 都描述了"确认简报"这个动作 |
| 14 | **竖版主体居中** | 居中裁切（`crop` 居中） | 真正的"主体居中"需要人脸/主体检测，PRD F3-3 未给方案。这是明确未实现项 |
| 15 | **短版切片** | 从第一段副歌起点起截 170 秒 | PRD F3-8 只说"可选短版（2:30–2:50）"，没说怎么选段 |
| 16 | **"强拍"容差** | 切点吸附最近强拍，容差 0.4 秒 | PRD 只说"对齐强拍（默认对齐强拍）" |
| 17 | **每行 6–12 字硬约束** | 生成时写进提示词，生成后用规则检查并在界面上标红越界行 | LLM 不一定稳定满足，所以做了"提示词约束 + 生成后校验"的闭环，而不是只靠提示词 |
| 18 | **锁定语义** | `timeline_clip.locked`：人工锁定后"重新自动卡点"不改动该片段（PRD F3-6 要求），但人工替换镜头会自动置 `manual=true`（不代表锁定） | — |
| 19 | **打标同步/异步** | 默认同步（上传即完成打标），`asset_tag` 任务类型已实现但未默认启用 | PRD F4-1 要求"上传后 1 分钟内出现在列表（打标可后台进行）"，同步实现已满足 1 分钟约束 |
| 20 | **预览播放器** | 音频驱动时间轴 + 按当前片段切换视频源并同步入点；竖版预览用 9:16 容器裁切 | PRD F3-3 要求"16:9 / 9:16 预览切换"。逐帧合成预览成本太高，实验室阶段用分段预览足够判断卡点与画面匹配 |
| 21 | **MiniMax 取用方式** | 适配器改为双模：官方开放平台 API（`MINIMAX_API_KEY`，api 队列并发 4）与本地自建服务（`MINIMAX_LOCAL_ENDPOINT`，gpu 队列串行 1）自动切换，官方 API 优先 | **PRD §13 的结论已过期**。原文判断"MiniMax 付费 API 已不对新用户开放"故定为本地 4090 部署；实际官方 Music 系列 API 已对外开放，且是三家门槛最低的（实名 + 支付宝，$0.15/首起）。因此改为双模——不买 GPU 也能让 MiniMax 参与三模型对比，将来想省成本再切回本地部署。附带修正：模型卡片上的名称/运行方式改为跟随 `.env` 实时显示，`available` 不再只在首次初始化时写一次 |

## 4. 仍需你拍板的开放项

1. **打标成本**：抽帧策略定了吗？按现在的 3 帧/条，1 万条素材 = 3 万次 VLM 调用。要不要先做镜头切换检测 + 抽样打标？
2. **竖版主体裁切**：要不要引入主体检测（人脸/显著性）？还是先接受居中裁切？
3. **字幕翻译时点**：当前在合成时翻译，每合成一个中英字幕版就翻一次。是否改成在歌词确认时翻一次并落库、多个版本复用？
4. **知识产权留痕**：PRD §13 关心"AI 生成结果与已有歌曲相似"的侵权风险。要不要在选曲环节强制记录一段"人工听辨确认"的签注？
5. **文化知识库**：现在史实核对没有可追溯依据。如果后续要做，最小的形态是什么——一份目的地条目表，还是可检索的文档库？

## 5. PRD 里我认为需要修正的地方

- **§1.4 范围表**把"合规审核台、版权溯源报告"放到后续版本，但 §13 风险表又把"侵权风险"和"平台低质量批量内容政策"列为 V1.0 的风险。这两项在有 P0 风险的同时没有对应的 V1.0 缓解手段（只有"不输入原曲"这类预防性约束）。建议至少在选曲/合成分支上留一个"人工听辨确认"的强制签注。
- **§11 合规**写"海外投放时打开平台 AI 生成内容标识"，但 §1.4 又把"多平台自动发布"排除在 V1.0 之外——V1.0 是人工上传（S6 步骤 1），所以这条是操作规范而非系统需求，建议移到 §1.2 说明里，避免验收时无从核对。
- **§5.1 体验指标**里"写词：歌词确认前人工修改行数 ≤ 30%"需要一个基线口径（哪些算"修改"——重写选中行算不算？采纳建议算不算？）。当前实现把两类都计入新版本，但没做统计埋点。
