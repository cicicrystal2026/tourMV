## 3. 端到端实测：从 0 到 1 完整跑通 ✅

我用一个全新项目「**E2E验证·婺源篁岭**」（目的地：江西·婺源）走了完整链路。
全程真实调用外部服务、真实花费、真实出片。

### 3.1 实测时间线

| 阶段 | 状态流转 | 实测耗时 |
|---|---|---|
| 创建项目 + 简报 | → `briefing` | 即时 |
| 写词（LLM） | `briefing` → `lyric_generating` → `lyric_review` | **12 秒** |
| 生曲（Mureka，1 模型 × 1 版） | → `music_generating` → `music_review` | **57 秒** |
| 逐句配图（Seedream 5.0，17 张） | → `storyboard_generating` → `storyboard_review` | **320 秒** |
| 音频分析（节拍 + whisper 对齐） | → `audio_analyzing` → `rough_cutting` | **39 秒** |
| 卡点粗剪（24 个片段） | → `edit_review` | **66 秒** |
| 多版本合成（6 成片 + 2 封面 + OCR 自检） | `rendering` → **`delivered`** | **280 秒** |

**纯机器时间 ≈ 13 分钟**（不含人工审核等待）。对比传统影视公司 6–10 周，这是产品的核心价值。

### 3.3 产出质量抽查

- **歌词**：17 行，正好匹配 150 秒档结构（主歌4/预副歌2/副歌4/主歌2/尾副歌3）；
  地标全部**真实可考**——婺源江湾、思溪延村通济桥、篁岭晒秋、李坑大夫第、汪口俞氏宗祠、
  晓起古驿道、星江河、思口思溪古樟、理坑尚书第、沱川砚山、石城晨雾。

  机器预审给出 11 条「建议通过」、5 条「需人工细看」，起到减负作用。
- **音频对齐**：`engine=whisper`，**17/17 句时间来自歌声**，匹配率 46%，

  音画同步「起点差 0.00 秒、时长差 0.01 秒」；片尾自动加「含 AI 生成画面」字卡。
- **可访问性**：横版 HTTP 200、25.1MB、`video/mp4`。

## 5. 待修复问题（按严重度排序）

### 🔴 P0-1 · 缺失必装依赖会导致**线上无法交付**

**现象**：所有成片都渲染成功、时长/分辨率/音轨/音画同步全部通过，
但「字幕自检」报 `未安装 OCR，无法核验字幕是否烧录（pip install rapidocr）` → `qc.ok=False`
→ `render_all` 抛 `RuntimeError: 出片未通过` → **项目永远停在「待精剪」，无法交付**。

**根因**：`rapidocr>=3.0` 只写在 `backend/requirements-optional.txt:20`，
**不在 `backend/requirements.txt`**。而字幕是文旅交付的**要件**，不是可选项。

**为什么这是线上问题（推断，需实测确认）**：发布流程用的是
`pip install -r backend/requirements.txt`，若线上沙箱同样不装 optional 依赖，
则**同一处会失败**。队列历史里已经出现过两次相同原因的 `render_all failed`（字幕项）。
> ⚠️ 严谨起见：本次**无法直接验证线上沙箱是否装了 `rapidocr`**（线上 `/api/system/info`
> 不暴露 OCR 状态，且线上无渲染历史可查）。建议把依赖移入 `requirements.txt` 重新发布后，
> **在线上实跑一个项目到「已交付」**来确认。

**建议修法**（二选一，推荐前者）：
- 把 `rapidocr>=3.0`（及 `onnxruntime`）移入 `requirements.txt`；
- 或让 OCR 缺失时降级为 `warn` 而非 `fail` —— 但字幕是交付要件，**不建议放宽**。

### 🟠 P1-1 · 成本口径不一致，看板会低估 12 倍

**现象**：同一个项目，`project.total_cost` = **¥0.324**，
而 `GET /api/projects/{id}/calls` 实时算出 `project_total_cost` = **¥3.9716**。

**影响**：看板、项目卡、成本卡片展示的都是 `total_cost` → **显示 ¥0.32，实际花了 ¥3.97**。
图片（¥3.57，占 90%）与 VLM 费用**没有写回** `project.total_cost`。

**建议**：统一以一处为唯一口径（要么实时聚合，要么每笔 ai_call 落库时同步回写 project）。

### 🟠 P1-2 · README / 文档与代码严重脱节

已过时项：表数量（16→24）、状态数（10→12）、路由数（52→115）、用例数（37→42）、
页面数（4→8）；「已知未完成」里写「热歌监控未接入定时采集」—— **今天已建好并挂上定时任务**。

**影响**：新人/协作者按 README 理解系统会得到错误认知；也让"待完成清单"失真。

### 🟡 P2-1 · 换解释器会**静默降级**，无任何提示

| 启动方式 | `clip_encoder` | 后果 |
|---|---|---|
| `backend/.venv`（项目 venv） | `chinese-clip` | 真实语义检索 ✅ |
| 系统/managed python | `hash-fallback` | **语义检索失效，退化成哈希匹配**，界面无任何提示 ❌ |

同类问题还有硬编码 Windows 路径：`services/distribute.py:30`（`D:\09_OPC\...`）、
`services/trends.py:27`（`D:\WPS_Storage\...`）、
`adapters/media.py:89-95` 与 `services/render.py:61-67`（字体候选含 `C:\Windows\Fonts`）。
线上跑 Linux，这些默认值必然失效（部分有 env 覆盖，但默认值误导且无告警）。

**建议**：启动时做一次「能力自检」并在看板显式展示降级项（现在只有 `/api/system/info` 有数据，前端没展示）。

### 🟡 P2-2 · 安全默认值偏危险

- `FORCE_MOCK` 代码默认 `True`（整站走假实现）；当前 `.env` 已设 `0`，但**线上必须显式设**。
- `ACCESS_PASSWORD` 为空即**完全不鉴权** —— 当前实测 `auth_enabled=False`。
  线上若沿用，任何人都能访问成片与后台；EdgeOne 上的成片直链也未见鉴权（PRD 已知项）。

### 🟡 P2-3 · `services/trends.py` 运行时动态导入外部脚本

`trends.py` 通过 `importlib` 导入与本仓库之外（另一目录）的 `monitor.py` 并调用其函数。
属稳定性/供应链风险，且该脚本路径硬编码。**今天新建的 `_probe/hot_scan.py` 已可完全替代它**
（自包含、无需外部脚本），建议后续把趋势采集切到新管线。

### 🟢 P3-1 · 后端已备但前端未接的 8 个能力

`logout`、`stateMachine`、`updateMusicModel`、`benchRun`、`alignStatus`、
`trendsStatus`、`syncTrends`、`jobs`（任务队列列表）。

其中 **`jobs` 最值得补**：现在出问题（如本次的 `render_all failed`）只能靠日志或直接调接口排查，
**看板上看不到队列详情与失败原因**，这是运维盲区。

### 🟢 P3-2 · 三项 Sidebar 占位未实现

简报确认台（V2.0）、合规审核台（V2.0）、发布排期（V3.0）。

### 🟢 P3-3 · 热歌资产界面看不到

今天入库的 **141 张热歌素材卡**（59 备忘录 + 82 周榜）目前**只能通过接口读**，
前端没有趋势卡片页；`brief.trend_card_ids` 也仍未接进生产流程。
