# 504 Gateway Time-out 排查与修复方案

> 现象：在自定义域名 `tourmv.migucomi.com` 上操作时偶发 **504 Gateway Time-out**，
> 表现为「点了按钮没反应 / 生不出歌词」。沙箱直连（`tourmv-pipeline.app.workbuddy.host`）没有这个现象。
> 定位时间：2026-10-12　结论：**歌词其实生成成功了，504 是「慢 + 超时预算太紧」造成的假失败。**

---

## 一、先给结论

我走域名实测触发了一次「确认简报，开始写词」：

| 观测项 | 实测值 |
|---|---|
| `POST /api/projects/{id}/advance` 返回 | **200（成功）**，但**耗时 13.9 秒** |
| 后台任务 `lyric_generate` | `done` 100% |
| 歌词结果 | **14 行**（主歌1×4 / 副歌×4 / 主歌2×4 / 尾副歌×2），`source=ai`，自动检查已完成 |

**所以不是「生不出歌词」，是请求慢到踩过超时线、被网关掐断，于是前端报 504。刷新页面就能看到歌词。**

---

## 二、三层原因（按贡献排序，全部有实测支撑）

### ① 沙箱后端本身就慢（根因）

| 接口 | 域名 | 沙箱直连 |
|---|---|---|
| `POST /api/projects/{id}/worklog/heartbeat`（空负载） | 1.7 / 2.3 / 3.8 s | — |
| `GET /api/projects` | 2.08 s | 2.12 s |
| `GET /api/jobs` | 2.56 s | 3.62 s |
| `POST /api/projects/{id}/advance` | **13.9 s** | — |

正常应该 100–300ms。**两边一样慢 → 瓶颈在后端，不在边缘。** 原因：

- 沙箱是**单进程**（uvicorn）+ **内嵌队列 worker** + **SQLite**
- 线上当时正同时跑 **5 个 `reembed_assets`**（CLIP 向量重算，CPU 密集），
  抢 CPU 与数据库写锁 → 前台请求被拖慢

### ② 边缘函数的超时预算太紧（把「慢」放大成 504）

`wenlv-mv-edgeone/edge-functions/api/[[default]].js`：

```js
const EO_TIMEOUT = { timeoutSetting: { connectTimeout: 6000, readTimeout: 12000, writeTimeout: 6000 } };
const MAX_ATTEMPTS = 2;         // GET/HEAD/OPTIONS 会重试
```

- `readTimeout` 只有 **12 秒**，而 `advance` 实测就要 **13.9 秒** → **已经在超时线外面**
- GET 失败重试 2 次 → 最坏累计 ~24 秒，**超过 EdgeOne 平台网关自己的等待上限**
  → 平台直接返回 **504 页面**
- **判据**：边缘函数自己失败时返回的是 **502 + JSON**（带 `error` 字段）；
  看到 **504 页面**说明是被平台网关掐的，不是函数返回的

### ③ 有接口是「同步调 LLM」，走域名必然超时

| 接口 | 是否同步 | 预期耗时 | 走域名 |
|---|---|---|---|
| `POST /api/projects/{id}/advance`（确认简报） | **异步**（只入队，worker 后台写词） | 2–14 s | 偶发 504 |
| `POST /api/projects/{id}/lyrics/generate` | **无条件同步**（`svc.generate` 内联调 LLM） | 12–40 s | **必然 504** |
| `POST /api/projects/{id}/lyrics/check` | 待核（`h_lyric_check` 是队列任务，接口可能内联） | 10–30 s | 很可能 504 |

注意：`/lyrics/generate` 的 `sync` 查询参数是**死参数** ——
函数签名里有 `sync: bool = False`，但实现里根本没用到，**每次都同步执行**。

## 三、修复方案

### P0-1　边缘超时与重试策略（改前端部署侧，最快见效）

```js
// readTimeout 12s 太紧：实测单个正常请求就可能 13.9s
const EO_TIMEOUT = {
  timeoutSetting: { connectTimeout: 6000, readTimeout: 60000, writeTimeout: 6000 },
};
// GET 也只在「连接失败」时重试 1 次，不要在 5xx 上重试（否则累计时间超过平台预算）
const MAX_ATTEMPTS = 1;
```

### P0-2　写词类接口异步化（根治）

- `POST /lyrics/generate`：改为默认**入队** `lyric_generate` 并立即返回
  （与 `advance` 现有做法一致：`_dispatch` 已经在入队，直接复用）；
- `POST /lyrics/rewrite`、`POST /lyrics/check` 同样改入队；
- 前端已有 `lyric_generating` 状态与轮询（`p.status === 'lyric_generating'` 时显示
  「AI 正在写词…」），把按钮从「等响应」改成「跳状态 + 轮询」即可。

### P0-3　别让后台批处理把单进程压死

- `reembed_assets` / `retag_assets` 这类 CPU 密集批处理：**限制并发**（建议 1），
  或改成**手动触发**而不是自动重跑（线上刚才同时跑了 5 个）；
- 长期方案：给 uvicorn 多 worker 或把队列 worker 拆成独立进程（SQLite 需换成 WAL + 串行写）。

### P1　（可选）长请求绕过边缘

给沙箱 CORS 放行 `https://tourmv.migucomi.com`，前端对「写词 / 重写 / 检查」这类长请求
**直接打 `ORIGIN`**（沙箱域名），彻底不受边缘超时影响。
代价：前端要知道源站地址；需确认跨域与鉴权（当前 `ACCESS_PASSWORD` 为空，不鉴权）。

### 附带：一个真 P0（已在线上复现）

线上任务记录里出现：

```
render_all failed: RuntimeError: 出片未通过：failed=[] qc=['横版 1920×1080 · 中文字幕：字幕', '竖版 …：字幕']
```

即 **「字幕自检」失败 → 交付卡死**。根因是 `rapidocr` 只写在
`backend/requirements-optional.txt`，但字幕是文旅交付的**要件**，线上按
`requirements.txt` 装依赖 → 没装 OCR → 自检失败。
**修法：把 `rapidocr` + `onnxruntime` 移入 `requirements.txt`。**

## 四、排查这类问题的方法（复用）

1. **同时打域名与沙箱直连同一个接口比耗时** —— 两边差不多＝后端瓶颈；只有域名慢＝边缘问题。
2. **看状态码区分责任方**：`502 + JSON`＝边缘函数自己失败（含 `error` 字段）；
   `504 页面`＝被 EdgeOne 平台网关掐断。
3. **看任务队列**：`GET /api/jobs`，按 `project_id` 过滤，看是不是后台任务在抢资源、
   或者业务本身失败（例如 LLM 报错）。
4. **别只看 200**：该站配了 `rewrites: /* → /index.html`，未知路径返回 200 HTML 兜底页。
