# 本地部署 MiniMax Music 3 可行性评估

> 评估对象：本机（Windows / RTX 4090 Laptop / i9-13900HX）能否跑 MiniMax Music 3 开源权重，
> 以及跑起来要多久、有哪些真瓶颈。
>
> 数据来源：本机实测（nvidia-smi / WMI / 实测下载速率）+ MiniMax 官方仓库 README
> （`github.com/MiniMax-AI/MiniMax-Music3`，2026-09-27 抓取）+ 社区实测报告。
> 评估日期：2026-09-27

---

## 一、结论先说

**能跑，但不能按官方推荐的方式跑。**

官方参考部署路径 **SGLang-Omni 明确要求两张 CUDA GPU**（README 的 Limitations 第 1 条原话：
"Inference requires two CUDA GPUs"），GPU0 跑 8B 全局 LLM 与八层 RVQ 自回归，GPU1 跑 Flow Matching
与波形解码。这台机器只有一张卡，**官方路径直接出局**。

必须改走**量化 + 分层卸载的单卡路线**（ComfyUI INT8 或 diffusers group offloading）。
这条路能通，代价是显存换时间。

**而真正的瓶颈不是显卡，是内存。** 见第五节。

| 判定 | 项目 |
|---|---|
| ✅ 可满足 | 显卡型号、CUDA 环境、磁盘、网络、CPU |
| ⚠️ 贴边 | 显存 16GB（官方/社区分档的下边缘） |
| ❌ 当前不满足 | **内存只剩 7.6GB 可用**（模型侧建议 32GB 空闲） |

## 三、模型侧硬指标

### 架构（官方 README）

```
歌词 + 音乐描述
      ↓
Global LLM (8B，由 Qwen3-8B 初始化)   ← 逐帧预测第 1 个 RVQ 码本，管长程结构
      ↓
Local LLM (0.6B)                     ← 补每帧其余 7 个声学码本
      ↓
隐状态融合
      ↓
Flow Matching (2.4B)
      ↓
Flow-VAE Decoder (123M)
      ↓
32 kHz / 16-bit 立体声 WAV
```

> 注意：模型卡与社区实测对采样率口径不一致（官方写 32 kHz，有实测报告为 44.1 kHz），
> 以实际输出为准，不影响可行性判断。

### 部署路径与显存分档

| 路径 | 要求 | 本机能否 |
|---|---|---|
| **SGLang-Omni**（官方参考） | **2 张 CUDA GPU** | ❌ 单卡 |
| diffusers 全精度直跑 | ~24 GB 显存 | ❌ 只有 16GB |
| diffusers + CPU offload | ~22 GB | ❌ |
| diffusers + group offloading | **~8 GB** | ✅ 可跑，慢 |
| **ComfyUI INT8 + tiled decode** | 官方低显存档（16–23GB 档） | ✅ **推荐走这条** |

社区在 **RTX 4090 / 24GB** 上实测：FP16 pruned DiT + INT8 文本编码器 + tiled decode，
**生成 3 分钟歌曲耗时 219 秒，峰值显存 19.9GB**。这是目前最可信的性能锚点。

### 体积（实测 API 清单）

| 项 | 体积 |
|---|---|
| 全仓库 | **57.4 GB**（88 个文件） |
| diffusers 必需子集 | **≈ 29 GB**（language_model 17.2 + transformer 9.7 + 其余 2.1） |
| 可跳过 | `qwen_7B/` 18.5 GB、`flowmatching_vae.pth` 9.8 GB（SGLang 路径用） |
| ComfyUI INT8 版（另仓） | **≈ 11.9 GB**（全 INT8）/ 14.3 GB（16/8 混合） |

### 能力边界（官方 Limitations）

- 不支持流式输出，只能整首生成完才拿到文件
- 文本提示上限 5,000 tokens
- 音频上限 9,000 帧 ≈ **6 分钟**（官方宣称最长 5 分钟）
- 段落标记与风格描述是**生成式引导，不是确定性保证**——出曲的调性、配器、结构可能不完全对齐要求
- **仅支持 CUDA**（Apple Silicon 跑不了）

### 许可

MiniMax Music 3 Community License：**允许商用**，需在产品中显著标注 "MiniMax-Music3"；
年收入超过 2000 万美元需另行取得授权。正式商用前建议逐条复核 LICENSE 原文。

## 四、性能预期：到底要等多久

| 场景 | 3 分钟歌耗时 | 峰值显存 |
|---|---|---|
| 台式 4090 / 24GB（社区实测锚点） | 219 秒 | 19.9 GB |
| **本机 4090 Laptop / 16GB，INT8 + tiled** | **估 6–11 分钟** | 估 13–15 GB |

推算依据：INT8 量化会把 DiT 计算拉长，tiled decode 把长曲切成块顺序解码，
再叠加笔记本卡的功耗墙与散热降频（长时间满载会掉频）。**取保守值，不要按 219 秒规划。**

对本项目的实际影响：

- 一轮要出 **2 首候选**（MiniMax 2 首），单轮 **估 12–25 分钟**
- MV 目标时长 2:30，在模型 5 分钟能力范围内，不需要拉满
- 作为**实验室验证阶段**（不是生产并发），这个等待时间完全可接受

## 五、三个真风险（按严重度排序）

### 风险 1：内存，不是显存 ⚠️ 最该先解决

模型自身 fp16 权重约 22GB，官方建议 **32GB 内存起**（因为开卸载时权重要在内存里中转）。
本机总内存 31.7GB 看着够，但**当前可用只有 7.6GB**——已经有约 24GB 被别的程序占着。

**这是会直接导致 OOM 杀进程的那一项。** 动手前必须把浏览器、其它 AI 工具等关掉，
把可用内存腾到 20GB 以上。显存不够是「慢」，内存不够是「崩」。

### 风险 2：16GB 显存贴边

16GB 落在官方分档的下边缘，只能用 INT8 权重 + tiled decode。
长曲（>3 分钟）必须开分块解码，**分块边界可能有轻微拼接痕迹**。
我们的 MV 是 2:30，风险不大；但别一上来就试 5 分钟满长度。

### 风险 3：质量预期要对齐

社区共识：MiniMax Music 3 的整体水准**介于 Suno v3.5 与 v4.5 之间**，
多轨层次与编曲完整度不如商业 SOTA（差距明显）。
**但它有一个明确优势：发音准确度是当前开源模型里最好的**——在 WildSongBench 上音素错误率
6.27%，低于所有同表开源模型。对**中文歌词咬字**这件事，这是最相关的指标。

换句话说：论「好听」，别期待 Suno 级；论「把中文歌词唱清楚」，它是目前开源最优选择。

## 六、推荐落地路径

### 第 1 步：独立环境，别动现有 conda 环境

`D:\AI\conda\envs\comfyui` 已经在用（torch 2.6.0+cu124），直接改它有炸掉现有工作流的风险。
建议**新建独立 venv 或 conda 环境**（Python 3.12），只装这一件事需要的依赖。
社区参考用 torch 2.9.1，若 2.6.0 跑不通再升级，**升级只在新环境里做**。

### 第 2 步：下载权重，走国内镜像

- 优先 **ModelScope**（官方组织 `minimax` 有镜像，国内直连快）
- 或 hf-mirror，只拉 diffusers 子集（≈29GB，44MB/s 下约 **11 分钟**），
  跳过 `qwen_7B/` 与 `flowmatching_vae.pth` 省 28GB
- 装在 **D 盘**（92GB 可用，留出 40–50GB 余量）

### 第 3 步：起服务并对接项目

项目的适配器已经预留了本地契约（`backend/app/adapters/music/minimax.py` 顶部注释）：

```
POST {MINIMAX_LOCAL_ENDPOINT}/generate
     body {lyrics, prompt, duration_s, vocal, seed} → {job_id}
GET  {MINIMAX_LOCAL_ENDPOINT}/jobs/{job_id}
     → {status, audio_path|audio_url, duration_s, bpm}
```

而模型原生接口是 OpenAI 风格的 `POST /v1/audio/speech`（`input` 放歌词、`instructions` 放音乐描述）。
**两者之间需要一层 wrapper**：把我们的契约翻译过去，并在返回时补上 `duration_s` 与 `bpm`
（用 librosa 或有声分析现算）。这一层我来写，约一个脚本的量。

然后在 `.env` 里填 `MINIMAX_LOCAL_ENDPOINT=http://127.0.0.1:9100`、`FORCE_MOCK=0` 即可接入；
该模型会自动进项目的 **gpu 队列（串行 1）**，不会和其它任务抢显存。

## 七、必须提醒的一件事：本地只有一家模型

走本地路线意味着**三模型对比里只有 MiniMax 是真实的**。
Mureka 与 ElevenLabs 仍是没有 API Key 就没有真链路（继续走 Mock）。

如果这轮实验室验证的目的是「验证三模型对比机制」，那本地部署**只解决三分之一**，
另两家该申请还得申请。如果目的只是「验证整条 MV 生产链路能跑通、能出真实成片」，
那本地这一家就够了。

## 八、成本对照（一条 MV，2 首候选）

| 方案 | 单条成本 | 前置门槛 |
|---|---|---|
| **本地 4090** | 约 ¥0.06 电费（350W × 20 分钟） | 一次性下载 29GB + 环境搭建 |
| MiniMax 官方 API | ≈ ¥2.2（$0.15/首） | ❌ **新用户已不可开通**（2026-08-20 起） |
| Mureka API | 约 ¥0.4（$0.03/首） | 最低充值 $30，不退 |
| ElevenLabs | 约 ¥6.5（$0.15/分钟） | 需国际信用卡 |

**本地路线的隐性成本是「时间」**：一条 MV 出 2 首候选要等 12–25 分钟，
而 API 是几分钟。实验室阶段可接受；要跑量就得考虑 API 或多卡。

## 九、一句话总结

**这台机器能跑，前提是三件事：换成量化单卡路线（不用官方双卡路径）、
腾出 20GB 以上可用内存、接受一首歌 6–11 分钟的等待。**
硬门槛（显卡/CUDA/磁盘/网络）全部满足，真正卡住你的那一项是内存，而那是最容易解决的一项。
